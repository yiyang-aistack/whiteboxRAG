whiteBoxRAG Product Overview & FAQ (Demo Knowledge Base)

1. Product Positioning

whiteBoxRAG is a lightweight, on-premise deployable Retrieval-Augmented Generation (RAG) system built on FastAPI, LlamaIndex, ChromaDB and Ollama. It is designed to run on a CPU machine with as little as 8GB of memory, with no external middleware such as Redis, MySQL or message queues: the vector store (./storage/vectordb), documents (./storage/documents), logs (./storage/logs), trace records (./storage/traces), task state (./storage/tasks), and knowledge base metadata are all stored as local files. Both the LLM and the embedding model default to the local Ollama (qwen2.5:7b and nomic-embed-text:latest); providers and keys are configured in .env. The BM25 index is an in-memory process structure that is lazily built on demand and not persisted to disk separately.

2. Default Parameters & Core Metrics

1. The service listens on port 8080 by default (HOST and PORT can be overridden in .env); the health check endpoint is /api/health.
2. The default retrieval mode is hybrid (retriever.mode = hybrid), a weighted fusion of BM25 keyword retrieval and vector semantic retrieval; the BM25 weight (retriever.bm25_weight) is 0.6, and the vector weight is derived as 1 minus the BM25 weight, i.e. 0.4.
3. Fusion score = BM25 weight × BM25 score + vector weight × vector score. Hybrid retrieval returns 5 chunks by default (retriever.top_k) and discards candidates whose fusion score is below the similarity threshold; that threshold (retriever.similarity_threshold) defaults to 0.5. The vector_store section also keeps component-level defaults of top_k=5 and similarity_threshold=0.1 as fallbacks when no retriever configuration is present.
4. Because the vector weight (0.4) is below the threshold (0.5), chunks that hit only on the vector path cannot cross the threshold on their own. The startup log will emit a weight/threshold combination warning for this. reroute_on_empty_route is therefore enabled by default: when one path returns empty (for example the BM25 index is still being built after a restart), its weight is handed over to the other path for that query. This degradation is recorded in debug_info.route_degraded and in the retrieval funnel.
5. The rerank count of the retriever (rerank_top_k) defaults to 10; rerank_enabled and query_rewrite_enabled are enabled by default. When reranking is disabled, rerank_top_k falls back to top_k.
6. Default document chunk size is 512 characters, chunk overlap is 128 characters, and the per-file upload limit is 10MB (document_parser.max_file_size).
7. Context compression is enabled by default, with a maximum of 2048 tokens after compression.
8. The API layer provides 60 endpoints (plus /api/health), grouped into six modules: knowledge base management, conversational QA, scenario management, quality evaluation, document optimization and system monitoring.
9. Default API rate limit is 60 requests per IP per minute. /static, /api/health, /docs, /openapi.json and /redoc are exempted from rate limiting.

3. Supported Document Formats

The default upload whitelist (document_parser.supported_formats) is PDF, Word (.docx and .doc), plain text TXT and Markdown (.md). Text extraction is handled by three extractors: PDF (pdfplumber, falling back to pypdf when missing), Word (python-docx) and TXT. Legacy binary .doc has limited compatibility; convert it to .docx first. Extractors for Excel (.xlsx and .xls) and PowerPoint (.pptx) are implemented (depending on openpyxl and python-pptx respectively) but are not in the default whitelist — add the extensions to that config item to enable uploads. On upload, the system first validates the file extension, then performs a file magic-number (MIME) check on recognised formats to prevent executables from masquerading as documents. When the runtime lacks libmagic, it degrades to extension-only validation with a printed warning.

4. White-box Tracing Capabilities

1. The system ships with built-in sentence-level attribution, done in two steps. First, citation verification: if [Document N] in an answer sentence points to a chunk that was actually fed into this prompt, it is marked as "citation verified" (evidence based on the citation). Only when no citation is available does the system fall back to a similarity heuristic — it compares the answer sentence against every sentence in the chunk (fine-grained) and the entire chunk (coarse-grained), taking the maximum of the two. The heuristic conclusions range across direct quote, summary rephrasing, low confidence, and unsupported inference (including no source); the business view collapses these into three labels shown to users: evidence-backed (✓, direct quote & summary), low confidence (!), unsupported inference (✗). Similarity-based conclusions are always heuristic hints, not fact checks. Sentences for which the tracing component itself fails (for example embedding backend down) are marked "unverified" and are not counted toward drift rate or hallucination rate.
2. The retrieval tracing panel has two views: Business Summary and Technical Detail. Business Summary is aimed at business admins: the first screen shows the KB match conclusion, followed by an overall summary of the Q&A session, the retrieval funnel (candidates → threshold filter → compression → entering the answer, with reasons for rejected candidates and tuning suggestions), a retrieval recall summary (with hit reasons), per-sentence confidence tracing, intelligent diagnostics and optimization suggestions, and quality metrics. Technical Detail is aimed at engineers: it shows the query rewrite trace, BM25, vector and fused retrieval comparisons, fusion calculation details, full retrieval parameters, sentence-level similarity scores, citation-annotated source verification, and the raw non-recall diagnostic log.
3. Two white-box actions are built into the funnel: on-demand full-database non-recall scan (POST /api/chat/miss-scan) and hypothesis analysis (selectively add/remove evidence chunks, regenerate the answer side by side with the original, and compare drift rate and sentence-level evidence attribution).

5. Non-recall Diagnostics

When a user expects a document to be retrieved but it does not appear, they can inspect the non-recall diagnostics (recall_diagnostic.enabled = true by default). The system attributes root causes into four categories: metadata filtering excluded it, score just below the threshold (borderline), only one retrieval mode hit it, or the query is missing keywords. It also provides finer-grained root-cause labels for potentially missed chunks, such as embedding mismatch, borderline threshold, missing keywords, or partial match. A full-database scan runs automatically only when retrieval results are empty or when debug mode is on; it scans at most recall_diagnostic.full_scan_limit (default 500) chunks, or it can be triggered on demand by clicking "Scan full database for missed recalls".

6. Quality Evaluation

The evaluation framework is rubric v2 with ten metrics grouped into four score categories: retrieval quality (retrieval_score_avg mean fusion score, retrieval_score_std score standard deviation), faithfulness (answer_faithfulness, semantic_consistency, citation_coverage), relevance (answer_relevance), and safety & format (hallucination_rate, rejection_accuracy, empty_response, response_length). Each metric is normalized against its own passing line (a value exactly at the line scores pass_score = 0.7). The overall score is a weighted average of these normalized scores: retrieval 0.15, faithfulness 0.45, relevance 0.15, safety & format 0.25, re-normalized against the actually evaluable metrics of this run. is_passing is the same overall score plus explicit hard gates (non-empty response, hallucination rate within limit, evaluable weight coverage >= 0.6), so the score and the conclusion cannot contradict each other. Evaluation results can be compiled into shareable reports via POST /api/evaluation/report and retrieved via GET /api/evaluation/report/{report_id}. Scores carry a rubric_version and are not directly comparable across versions or scenarios.

7. Deployment

1. One-command startup: uv run python main.py --install. The script runs uv sync --locked first to create a .venv and install the locked dependencies, then performs environment checks and starts the service. For daily use run uv run python main.py. The service refuses to start when .env is missing.
2. Container deployment: build the image from deploy/Dockerfile, or simply run docker compose up -d which brings up Ollama, pulls qwen2.5:7b and nomic-embed-text, and starts the app in one command. Inside the container, localhost points to the container itself, so OLLAMA_BASE_URL must be passed explicitly.
3. Production mode: run the app with Gunicorn using single-worker, multi-threaded mode, for example uv run gunicorn --bind 0.0.0.0:8080 --workers 1 --threads 4 --timeout 120 api.api:app, or uv run gunicorn -c deploy/gunicorn.conf.py api.api:app.

8. Frequently Asked Questions

Q: Why is single-worker operation recommended?
A: The vector-store client and the BM25 index live in process memory. Multiple workers would each maintain their own copy of the state, leading to inconsistent indexes and caches across processes.

Q: Can it run without a local GPU?
A: Yes. The system is designed for CPU environments and runs quantized 7B models (for example qwen2.5:7b) via Ollama, which is sufficient for Q&A over small to medium knowledge bases. Recommended minimum: 8GB memory, 4-core CPU, 20GB available disk.

Q: Does my data leave the corporate network?
A: No, by default. Document parsing, embedding, retrieval and generation all happen locally. Cloud APIs are invoked only when LLM_PROVIDER or EMBEDDING_PROVIDER in .env is explicitly switched to openai; generation and embedding are independent switches.

Q: Does high similarity mean the sentence is definitely correct?
A: No. Only a sentence that carries [Document N] and that document is actually present in the current context counts as "citation verified" — that is evidence. Direct quote, summary rephrasing, low confidence and unsupported inference as returned by similarity are all heuristic hints for manual review, not fact checks. When the tracing component fails, the sentence is marked "unverified" and is not counted toward drift rate or hallucination rate.

Q: After a restart, will the first query fail to retrieve anything?
A: No. The BM25 index is lazily built on demand. Retrieval waits for any in-progress index build, up to bm25.build_wait_ms (default 500 ms), before degrading to the remaining path. If one path eventually returns empty, reroute_on_empty_route (enabled by default) hands its weight over to the other path, preventing the situation where "the vector path clearly recalled content, but it was filtered below the threshold because its weight was too low".
